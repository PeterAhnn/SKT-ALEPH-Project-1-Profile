# 합성 로그인 요청 재생에서 제한 기준이 과다 요청 허용과 정상 이용 손실에 미치는 영향

## 초록

로그인 요청 제한은 과다 요청을 줄이지만 정상 이용도 거부할 수 있다.
본 연구는 제한 기준을 IP·계정·복합으로 바꾸면 이 두 결과가 어떻게 달라지는지 확인했다.
네 합성 시나리오에서 각각 30개 시드와 200요청을 만들고, 같은 요청열을 제한 없음과 한도 5·10의 일곱 조건에 재생했다.
입력 24,000건에서 실제 로컬 판정 168,000건을 수집했다.
분산 출발지의 단일 계정 조건에서 한도 5의 과다 요청 허용률은 IP 단위 89.042%, 계정 단위와 복합 제한 각각 6.250%였다.
반대로 단일 출발지의 여러 계정 조건에서는 IP 단위가 6.250%, 계정 단위가 88.979%였다.
공유 IP의 정상 요청 거부율은 IP·복합 제한에서 95.000%였고, 동일 계정 혼재 조건에서는 계정·복합 제한에서 95.500%였다.
따라서 H1은 지정한 합성 조건에서 지지되지만, 제한 기준은 요청 분포와 정상 이용 손실을 함께 보고 선택해야 한다.
이 결과는 실제 계정 침해 성공률이나 운영 서비스의 오탐률 추정이 아니다.

## 1. 서론

### 1.1 연구 질문과 후보 선택

본 연구의 관심 분야는 정보보안이며, 로컬 환경에서 방어 방법의 효과를 측정하는 데 초점을 맞췄다. AI가 제안한 질문 10개를 비교한 뒤 작성자는 로그인 요청 제한 기준 비교를 선택했다. 후보 전체와 변수·측정법 검토는 `docs/RESEARCH-QUESTIONS.md`에 보관했다.

| 검토한 질문 | 이번 연구의 선택 |
|---|---|
| Q01 계정·IP 요청 제한 기준 | 최종 주제로 선택했다. |
| Q02 로그 비식별화 방식 | 별도의 민감정보 정답 자료와 출력 대응 준비가 필요하므로 이번 범위에서 제외한다. |
| Q03 암호 해시 반복 횟수와 비용 | 주 측정값이 처리 비용이며 요청 차단 효과를 직접 측정하지 않으므로 제외한다. |
| Q04 로그인 실패 탐지 시간창 | 사건·경보·중복 집계 정의가 필요해 연구 범위가 넓어지므로 제외한다. |
| Q05 정규식 구조와 처리 시간 | 입력 검사 성능의 별도 연구 후보로 남긴다. |

### 1.2 선행 연구와 새로 확인할 내용

DALock 연구는 실제 암호 자료를 사용한 시뮬레이션으로 공격 억제와 정상 사용자 불편의 상충 관계를 평가했다[1]. 이 문헌은 본 연구에서 과다 허용률과 정상 거부율을 함께 측정하는 근거이다. NIST의 인증 지침은 계정의 특정 인증수단에 대한 연속 실패 제한과 정상 사용자가 잠기는 부작용의 완화를 다룬다[2]. 이 지침은 계정 기준을 비교에 포함하는 근거이며 이번 제한기의 성능을 입증하는 실험 결과는 아니다. StopGuessing은 IP 기반 판단에 암호 분포·오타 등 추가 특성을 결합해 시뮬레이션하고 입력 가정의 영향을 설명했다[3]. 이 문헌은 공유 IP 조건과 합성 실험의 일반화 한계를 검토하는 근거이다.

제한에 보안과 사용성의 상충 관계가 있다는 점은 기존에 알려진 사실이다. 이번에 직접 확인하는 것은 동일 합성 요청열에 단순 이동 시간창 정책을 적용했을 때의 요청 단위 결과와 그 차이이다. 학술적으로 최초의 방법이거나 기존 연구보다 우수하다는 신규성 주장은 하지 않는다.

문헌은 출판 기관·저자 원문의 서지 페이지와 초록·관련 본문을 직접 열어 제목·저자·연도·내용을 확인했다. 확인 구간은 `docs/LITERATURE.md`에 기록했다. OWASP Authentication Cheat Sheet도 검토했지만 고정 발표 연도와 판본이 확인되지 않아 채택 참고문헌에서는 제외했다. 연도를 추정하지 않고 연도가 확인된 세 문헌으로 근거를 구성했다.

### 1.3 가설과 반증 결과

**H1: 여러 IP에서 한 계정으로 요청하는 조건에서, 계정 단위 제한은 IP 단위 제한보다 과다 요청 허용률을 낮춘다.**

‘IP 단위’는 같은 합성 출발지 식별자를, ‘계정 단위’는 같은 합성 계정 식별자를 각각 하나의 누적 키로 사용한다는 뜻이다. ‘과다 요청’은 생성 전에 attack으로 지정한 시험 입력이며, 제한기에 정답 라벨을 제공하지 않는다. 허용률은 해당 요청이 제한기를 통과한 비율이다.

반증 조건은 주 조건에서 계정 단위 허용률이 IP 단위와 같거나 더 높아지는 결과이다. 같은 시드의 IP 허용률에서 계정 허용률을 뺀 Δ 평균이 0보다 크면 지정 조건에서 H1을 지지하고, 0 이하이면 지지하지 않는다고 본실험 전에 정했다. H1을 모든 요청 분포의 우월성 주장으로 확대하지 않았다.

## 2. 방법

### 2.1 실행 환경과 사전 설계

Windows 11, AMD64, CPython 3.14.6에서 Python 표준 라이브러리만 사용했다. 외부 서버에 접속하지 않고 요청 제한기를 직접 호출하는 로컬 재생 실험이다. 본실험은 2026-10-16T08:11:07.770677+00:00에 시작해 08:11:09.654362+00:00에 끝났다. 실제 프로그램 실행 소요 시간은 약 1.884초이며, 이것은 연구 준비·검토·문서 작성 전체의 소요 시간이 아니다.

설계·가설·시나리오·분석 규칙은 본실험 전에 `docs/PROTOCOL.md`에 기록했다. 08:11:05.620083+00:00에 설계와 실행 소스의 SHA256을 `verification/protocol-lock.json`에 보관했다. 이는 로컬 사전 설계이며 외부 사전등록 서비스에 등록한 연구는 아니다.

예비 실행은 각 시나리오 시드 1의 요청 800건·판정 5,600건을 별도 폴더에서 두 번 만들었다. CSV 세 파일이 바이트 단위로 같음을 확인했다. 예비 자료는 본실험에서 제외했다. 예비 실행 뒤 설계 변경은 없었다. 본실험 뒤 문서의 요청 식별자 표기 event_id를 실제 필드명 request_id로 설명 정정한 사실은 `docs/PROTOCOL-ERRATA.md`에 남겼으며 원래 설계 파일은 보존했다.

### 2.2 독립변수와 통제 조건

독립변수는 제한 기준과 허용 한도이다. 제한 기준은 없음·IP 단위·계정 단위·복합의 네 종류이다. 제한 없음은 한도 0으로 표시하고, 나머지는 한도 5와 10을 사용해 총 일곱 조건을 만든다. 한도 5는 주분석, 한도 10은 본실험 전 지정한 민감도 분석이다.

모든 조건은 직전 60,000ms의 허용 요청만 세는 이동 시간창을 사용한다. 현재 시각 t에서 유효한 이력 구간은 (t−60,000, t]이다. 거부된 요청은 누적하지 않는다. 복합 제한은 IP와 계정 키를 각각 확인하고 하나라도 한도에 도달하면 거부한다. 통과한 요청만 두 키에 함께 추가한다. 정답 라벨과 자격 유효 여부는 허용 판정에 사용하지 않는다.

이 실험은 인증 전에 모든 허용 요청을 세는 입장 제한기이다. NIST의 연속 인증 실패·성공 후 초기화·인증수단 비활성화 규칙을 그대로 구현한 준수 검증이 아니다. 한도 5·10과 60초 창은 비교용 설정이며 실제 서비스 권장값으로 제시하지 않는다.

### 2.3 합성 원자료와 반복 범위

| 시나리오 | 과다 시험 요청 | 정상 시험 요청 |
|---|---|---|
| distributed_target | 160건. 20개 합성 IP가 한 계정에 각 8건을 보낸다. | 40건. 별도 정상 계정·IP 조합 20개에 각 2건을 배치한다. |
| single_source_spray | 160건. 한 합성 IP가 20개 대상 계정에 각 8건을 보낸다. | 40건. 별도 정상 계정·IP 조합 20개에 각 2건을 배치한다. |
| shared_nat_benign | 0건 | 200건. 50개 정상 계정이 합성 IP 하나를 공유하며 각 4건을 보낸다. |
| targeted_mixed | 160건. 20개 합성 IP가 같은 계정에 각 8건을 보낸다. | 40건. 20개 정상 합성 IP가 같은 계정에 각 2건을 보낸다. |

시나리오별 시드 1~30에서 각 200요청을 생성했다. 난수는 Random(1000003 × 시나리오 인덱스 + seed)로 고정했다. 인덱스는 위 표 순서의 0~3이다. 논리 시각은 정수 0~119,999ms에서 균등 추출하고, 시각과 생성 순번으로 정렬했다. 실제로 120초씩 기다린 실험이 아니다. 정상 요청의 자격 유효 확률은 0.9이고 과다 요청의 자격은 모두 무효이다. 본실험에서 정상 유효 입력은 8,621/9,600건이었다. 이는 지정 확률의 난수 실현값이다.

생성 입력은 4 × 30 × 200 = 24,000건이며, 같은 입력을 일곱 조건에 재생하여 판정 168,000건과 반복별 집계 840행을 수집했다. 반복의 기본 단위는 시나리오별 30개 요청열이다. 모든 판정 건을 독립 표본으로 세지 않았다. 공개 원자료를 내려받은 연구가 아니며 원자료는 실제 생성·실행 시각과 함께 보관했다.

### 2.4 지표·분석·원자료 검증

과다 요청 허용률은 허용된 attack 요청 수/전체 attack 요청 수 × 100, 차단률은 차단된 attack 요청 수/전체 attack 요청 수 × 100이다. 정상 요청 거부율은 제한된 benign 요청 수/전체 benign 요청 수 × 100이다. 정상 이용자의 입력 실수는 benign을 유지한다. 허용된 무효 자격은 로컬 상태 코드 401, 유효 자격은 200, 제한 거부는 429로 출력한다. 실제 HTTP 응답을 전송한 결과는 아니다.

분모가 0인 공유 IP 정상 시나리오의 과다 허용률·차단률은 계산 불가로 표시하고, CSV는 빈칸·JSON은 null로 보관했다. 시드별 평균·표본 표준편차·최솟값·최댓값은 `results/summary.csv`와 `results/RESULTS.md`에 전부 제공한다. 같은 조건의 요청 수가 같으므로 전체 합계 비율과 시드별 비율 평균이 일치한다.

주분석은 같은 시드의 IP와 계정 허용률 차이 30개를 대응시켜 평균했다. 참고용 재표집 구간은 30쌍을 함께 재표집하는 bootstrap 10,000회, seed 20261016, 선형 보간한 2.5·97.5백분위이다. 이 구간은 합성 생성기의 시드 변동을 나타내며 현실 이용자 집단의 신뢰구간으로 해석하지 않는다. 구간이나 유의확률을 H1 판정에 사용하지 않았다.

분석기는 CSV의 SHA256·크기·행 수, 일곱 조건의 동일 요청열, 입력과 판정의 request_id 연결, 상태 코드와 허용 여부를 검증했다. 판정에서 다시 집계한 값은 runs.csv와 모두 일치했다. 별도 직접 검산에서도 모든 판정의 같은 키에 대한 직전 허용 이력 점유 수가 판정과 일치했다. 본실험에는 정확히 60,000ms 경계의 같은 키 이력이 없었으므로 경계의 등호 동작은 예비 확인에서 검증한 범위로 구분한다.

주 결과의 분자는 `data/main/raw/decisions.csv`에서 scenario가 distributed_target, threshold가 5, actor_label이 attack인 행 중 policy가 ip 또는 account이고 allowed가 true인 행의 수이다. 분모는 같은 조건의 attack 행 전체이다. 대응 단위는 seed이고 개별 요청은 request_id로 입력 CSV에 연결한다. `raw/runs.csv`의 attack_allowed·attack_attempts로 같은 값을 확인하고, `results/paired_differences.csv`에서 시드별 Δ를 확인할 수 있다.

## 4. 논의

### 4.1 지지된 부분과 다른 결과의 해석

여러 출발지의 시도가 같은 계정 키로 합쳐지는 조건에서는 계정 기준이 허용 기회를 줄였다. 반대로 한 출발지의 시도가 여러 계정으로 나뉘면 IP 기준이 더 적은 과다 요청을 허용했다. 두 결과를 함께 보면 제한 식별자와 요청의 집중 위치가 결과를 결정하는 핵심 조건임을 확인할 수 있다.

공유 IP에서는 IP·복합 제한이 정상 요청의 95%를 거부했다. 동일 계정 혼재에서는 계정·복합 제한이 정상 요청의 95.5%를 거부했다. 복합 제한은 공격 허용을 낮춘 조건에서도 정상 이용 손실을 그대로 포함했다. 따라서 이번 결과를 복합 제한의 보편적 우월성으로 읽을 수 없다.

### 4.2 대안 설명과 설계 구조의 영향

반대 결과를 설명할 가능성으로 요청의 집중 위치, 키별 요청량과 한도의 관계, 정상·과다 요청이 같은 키를 공유하는지를 검토했다. 입력 CSV의 계정/IP 대응을 확인하면, 분산 조건은 한 계정에, 스프레이 조건은 한 IP에 요청이 집중한다. 공유 IP와 혼재 조건은 각각 IP 할당량과 계정 할당량을 정상 요청이 함께 사용한다.

분산·스프레이의 별도 정상 조합은 키당 총 2건, 공유 IP의 정상 계정은 총 4건이므로 계정 한도 5 아래의 0% 거부는 구조상 예상되는 결과이다. 한도 10에서 분산 IP나 스프레이 계정은 키당 총 8건뿐이므로 관련 허용률 100%도 설계로 설명된다. 이런 값은 현실 오탐률의 추정이 아니다. 결과 차이는 정해 둔 시험 조건의 작동 방식이며 실제 인터넷에서 발견한 현상으로 표현하지 않는다.

H1 문장은 수정하지 않았다. 다른 결과를 보고 모든 정책을 대상으로 새 우월성 가설을 사후에 만들지 않았고, 원래 가설과 사전 비교군을 함께 보존했다.

### 4.3 한계

이 연구는 네 합성 분포와 두 한도, 하나의 시간창에 한정된다. 생성 규칙을 현실 이용자의 행동 분포로 보정하지 않았고 실제 서비스 로그도 사용하지 않았다. 허용은 제한기 통과이며 모든 과다 자격이 무효이므로 실제 로그인 성공·계정 탈취 성공을 측정하지 않는다. 합성 IP 식별자, 논리 시각, 로컬 응답 코드는 실제 네트워크 출발지·지연·HTTP 서버 동작의 증거가 아니다.

다중 서버의 상태 동기화, 신뢰할 프록시 판정, 실패 횟수 기반 잠금, 성공 후 초기화, MFA와 복구 흐름은 다루지 않았다. NIST 준수나 DALock·StopGuessing 대비 성능을 입증하지 않는다. 반복 30회와 재표집 구간은 생성기 시드의 변동만 보여 주며 현실 서비스 모집단으로 확대하지 않는다. 실제 적용의 최적 한도·창 길이·정상 손실 허용 수준은 추가 자료와 요구사항이 있어야 정할 수 있다.

### 4.4 최종 결론

분산된 단일 계정 요청에서는 계정 제한이 효과적이지만, 제한 기준은 요청 분포와 정상 이용 손실을 함께 보고 선택해야 한다. 이 결론은 작성자가 결과 요약을 확인한 뒤 채택했으며 적용 범위는 이번 합성 로컬 실험으로 한정한다. 주 조건의 과다 요청 허용률은 IP 89.042%, 계정 6.250%로 달랐지만, 스프레이 조건에서는 방향이 반대였고 공유 IP·동일 계정 혼재에서는 각각 다른 정상 이용 손실이 나타났다. 어느 제한 기준이든 요청의 집중 위치와 공유 구조를 고려해야 하며, 이 수치만으로 운영 서비스의 안전성이나 보편적 최적 정책을 단정할 수 없다.

## 부록 A. 짧은 재현 방법

ZIP을 새 폴더에 풀고 Python 3.14.6을 준비한다. 외부 라이브러리·계정·API 키·네트워크 접속은 필요하지 않다. 다른 Python 버전은 이번 검증 범위 밖이다.

```powershell
python -X utf8 -B scripts/reproduce.py
```

새 reproduction 폴더의 verification.json에서 passed가 true인지 확인한다. 요청·판정·반복 집계·조건별 요약·대응 차이 CSV 다섯 개가 제공 원자료와 SHA256까지 일치하면 재현 통과이다. 실행 시각을 담는 manifest는 바이트 일치 대상에서 제외한다. 기본 실행은 기존 원자료와 결과를 덮어쓰지 않는다.

실패하면 Python 버전, 압축 해제 파일 누락, 오류 전문을 확인한다. 기존 출력 폴더를 재사용하지 말고 새 경로를 지정한다. 파일 해시가 다르면 원자료를 고쳐 맞추지 말고 verification.json의 실패 항목과 오류를 보존한다.

## 부록 B. AI와 작성자의 판단

AI에게 맡긴 일: 질문 10개와 가설 후보 비교, 문헌 검색·서지 확인, 사전 설계와 Python 구현, 합성 입력 생성·로컬 실험·집계·재현 확인, 논문 초안 정리를 맡겼다.

내가 판단한 일: 정보보안 분야와 로그인 요청 제한 비교를 선택했고, 결과 요약을 확인한 뒤 요청 분포와 정상 이용 손실을 함께 보아야 한다는 결론을 이번 합성 로컬 실험의 범위에서 채택했다.

AI 말을 안 들은 일: 이번 대화에는 명시적으로 거절한 AI 추천이 기록되지 않았다. 추천한 연구 주제와 실제 선택이 같았고, 결과 해석은 확인 후 채택했다. 대안 후보를 선택하지 않은 사실을 AI 추천 거절로 바꾸어 기록하지 않는다.

선택·승인·결론 채택의 실제 기록은 docs/DECISIONS.md에 보관한다. 자동 분석 JSON은 사용자 확인 전에 만든 수치 판정 기록이므로, 사용자 최종 판단은 이 부록과 결정 기록을 기준으로 확인한다.
